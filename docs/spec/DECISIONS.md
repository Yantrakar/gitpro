# Decisions on the review's product-owner questions

Made by the orchestrating agent on 2026-10-02 while the product owner was away,
choosing the conservative option each time. Each one is easy to revisit; the
spec follows these until the product owner says otherwise.

| Q | Decision | Why |
|---|---|---|
| Q1 paid tier | Everything in this repo stays MIT and free, including 14 (policy, `check --policy`, the Action). Paid ideas (hosted GitHub App, team dashboard) stay in 14's "future, needs hosting" section only. | The owner asked for ideas on a paid tier, not for a licence change. Nothing built now is lost if a paid tier comes later. |
| Q2 `forge similar` | Keep. Off by default; needs `--send-repo-names` on every run (or `[forge] similar = true`), and the first line says exactly what is sent to which service. | The owner asked for "discovery of similar work on github public". |
| Q3 shell history in `discover` | Opt-in: `--history`. Without it, discover reads editor recents, ssh config host aliases, includeIf rules and repos on disk only. Output never echoes history lines, only the clone URLs found. | History can hold secrets; local-only still deserves consent. |
| Q4 guard defaults | **Reversed on 2026-10-15 (spec 21 D4): `gitpro setup` installs the guard; `[guard] hooks = false` opts out.** Before that: nothing installs until the user runs `guard install` (or sets `[guard] hooks = true`). Once installed: `on_mismatch = "block"`, pre-commit and pre-push both on, global mode (core.hooksPath) with chaining fixed per review R-001/R-003; per-repo mode available. The guard judges the committer (the user's own identity), per R-005. Any gitpro failure fails open. | The owner asked for a guard; an installed guard that only warns is easy to ignore. Opt-in install keeps it safe. |
| Q5 tracked team files | gitpro never writes tracked files (devcontainer.json, `.husky/*`, `.claude/settings.json` in a repo, `.mcp.json` in a repo) by default; it prints the snippet. An explicit `--write` exists only for devcontainer.json and project `.mcp.json`, with backup and undo. User-level files (`~/.claude/settings.json`) follow the normal preview/confirm/backup/undo rules. | Writing files a whole team commits is a team decision. |
| Q6 agent hook bypass | The agent is told to ask the user; the message does not teach a bypass. The user bypasses with `GITPRO_SKIP=1` in their own shell, `[agents] hook = "warn"` or `"off"`. Warn mode emits no permission decision (the normal permission prompt still happens) plus a visible message. "block" emits deny. Never emit allow. | R-006: allow would skip the user's own permission prompt. |
| Q7 PyPI | Not assumed. Install docs keep `pipx install git+https://github.com/Yantrakar/gitpro.git`; the Action installs from its own checkout (`pip install "$GITHUB_ACTION_PATH"`). | Owner has not claimed the PyPI name. |
| Q8 devcontainer & Windows | Print-only by default; `--write` warns that the snippet needs `gitpro` on every teammate's host and uses a form that does not fail the container build when gitpro is missing on any OS. | Do not break teammates. |
| Q9 scope | All packages are built (the owner asked for all), in the review's order: 01, 06, 10, 12, 15, 16 first; then 02, 03, 07, 08, 09, 11; then 04, 05, 13, 14; 17 last. | Owner's instruction "implement all". |
| Q10 other agents | Claude Code adapter fully built and tested. Cursor / Gemini adapters exist in the adapter table, marked experimental, not installed unless named explicitly. | Their hook formats are unverified offline. |
| Q11 glab one login per host | Accepted and documented. | glab limitation. |
| Q12 versions | One version for CLI, extension and plugin. The extension detects features with `gitpro --version` and a `capabilities` list in `gitpro --version --json`, not a hard minimum. | Simpler and robust to mixed installs. |

## Decisions made during implementation (2026-10-02)

Taken by the implementing and QA agents where the spec was silent, wrong or
unsafe as written. Each row says what shipped and why. Where a row departs
from a package file, this table wins; the package files were not rewritten.

| package | decision | why |
|---|---|---|
| 01 / 11 (follow-ups) | Remote URLs that gitpro shows to users or MCP clients, or writes to JSON, are masked by `resolve.redact_url`. A password in the userinfo becomes `user:***@`, a bare token in an http(s) userinfo becomes `***@`, and the values of secret query parameters (`access_token=`, `private_token=`, `token=`, `sig=` and the others in `SECRET_QUERY_KEYS`) become `***`. The VS Code log masks commands the same way (`exec.ts` `SECRET_KEYS`, kept in sync). The masking is for display only: matching and git use the real URL. `lost` keeps its own `redact` (`[REDACTED]`, plus GitHub/GitLab token shapes in warnings). `core.sshCommand` values are shown verbatim: they are not URLs, so a secret inside a user's own `sshCommand` is not redacted (documented in the README). | A token in `https://user:token@host/…` or in a signed URL's query must never reach a terminal, a log or an agent. A command line has no reliable secret syntax to redact. |
| 03 | `lost` avoids partial-clone lazy fetches: `status --no-renames`, `GIT_NO_LAZY_FETCH`, and on git < 2.44 a missing-object probe that reports "could not compare". Every git call runs with `protocol.allow=never`. It runs no lfs filters during `status`; other clean filters can still run (documented). | A read-only scan must never touch the network, and `lost` must stay fast on big partial clones. Blocking every filter would make `status` report wrong results. |
| 03 / 09 | `[forge] online = true` in the config never hard-fails: when `gh`/`glab` is missing, the command falls back to offline with a `⚠`. Only an explicit `--online` exits 2. `lost` gained `--offline`, which the VS Code view always passes. | A config default must not break offline machines. An explicit flag is a request the user can see failing. |
| 04 | `discover` calls `gh`/`glab` directly with token variables stripped from their environment and never runs `gh auth token`. A suggested block with fields gitpro could not find gets `""` plus a fill-in comment. | Discovery needs logins, not tokens. Empty strings fail validation loudly, so a pasted block cannot be applied half-filled. |
| 05 | The forge library takes a `Session`. A failure for one account is a `⚠` and that account is skipped. When glab's single login per host does not match the identity's `glab_account`, that account is skipped too. `forge similar` uses `gh` only. | One broken login should not hide the other accounts. A mismatched glab login would answer for the wrong account (Q11). |
| 06 | The `push-to-checkout` hook is not installed or forwarded. | Installing it would break `receive.denyCurrentBranch = updateInstead`. |
| 06 (round 2) | A `chain_to` directory deleted after install no longer blocks an unrelated `apply`: it warns and renders the hooks without the chain. An explicit `guard install` still refuses. The hook head unsets `CDPATH`. | `apply` should not fail because of a stale hook setting. `guard install` is the place to fix it. `CDPATH` can make `cd` in a hook print paths or go to the wrong directory. |
| 07 | An identity with `ssh_alias` and `ssh_port` always clones through the scp form `user@alias:owner/repo.git`. An existing empty target directory is an error. The `owner/repo` shorthand works with `--identity`. | The ssh `Host` block carries the port, and an `ssh://…:port` URL would match no `includeIf` pattern. Refusing an empty directory avoids cloning into a directory the user made for something else. |
| 07 (follow-up), superseded by the follow-ups package | VS Code clone cancel sends SIGTERM to gitpro's process group (gitpro alone on Windows), then waits up to 10 s for gitpro itself to exit (`Child.exited`), not for the directory to disappear. If the directory is still there, the user is told to remove it by hand. | The first version had no child handle and could only poll the directory. `exec.ts` now hands out the child, so the wait is for the cleanup itself. |
| 08 | The `commit-msg` deny has no `GITPRO_SKIP` hint. Only the user's own commits are judged by the trailer policy; merges are exempt from `require`. `--rewrite` uses `commit-tree` plus one guarded `update-ref` (no rebase), and refuses merge commits and anything pushed to any remote. The default audit covers all unpushed commits plus the newest 1000 pushed ones (`--all` for everything). `[bot]` in agent and forbid globs is always literal. | Q6 for the hint. Colleagues' commits and merges are not the user's to fix. A single guarded ref update is atomic and easy to undo. A cap keeps audit fast on huge histories. `[bot]` would otherwise be a character class. |
| 08 (QA) | `--rewrite` signs the new commits when `commit.gpgsign` is true and keeps the exact bytes of colleagues' commits. "Pushed" means reachable from a remote-tracking ref as of the last fetch (documented). | A signing repo must stay signed. Fetching is the user's call; gitpro stays offline. |
| 09 | `keys --health` detects keys without a passphrase with `ssh-keygen -y -P ''` (stdin `/dev/null`, output discarded); gitpro itself never opens a private key. A group-writable `.pub` is `⚠`, not `✗`. | ssh-keygen answers the question without gitpro reading key material. A writable public key is a risk but does not stop ssh from working. |
| 10 | The deny reason never mentions `GITPRO_SKIP` (Q6 over the spec's example). Warn mode uses `systemMessage`. `--continue` is still judged (it commits); `--abort`, `--quit`, `--skip`, dry runs, help and read-only `gh api graphql` are exempt. | The agent must ask the user, not route around the check. `--continue` creates a commit; the exempt forms do not. |
| 10 (round 2) | A repo directory the hook cannot know (`$VAR`, `$(...)`) is judged at the known prefix or the cwd. A repo alias is resolved with a read-only `git config --get alias.X` and never followed for `!` aliases. The bypass is documented to humans in `agent status` and `--help` only. | Judging somewhere beats skipping. Running a `!` alias would execute code. Humans need to find the bypass; the agent should not be told. |
| 13 | `initializeCommand` is a single multi-line string, not the spec's array. Line 1 is `command true \|\| exit 0`, which stops Windows cmd. The `exit` is on the `read` line, so a newline in the workspace path cannot inject commands. Merging into the object form runs the user's own command in parallel with `pin`, and gitpro says so. | The devcontainer CLI runs a string through `/bin/sh -c` or `cmd /c` but runs an array directly, and the array form fails with ENOENT on Windows (V-030). The Windows behaviour is reasoned, not run on Windows (documented). |
| 13 | `--write` refuses a symlinked `devcontainer.json` whose target is outside the repo. `--json --write` needs `-y`. | Only repo files are in scope. JSON mode never asks questions (README §6). |
| 14 | In `--range` (CI) mode, an in-repo policy is read from the range base (`git show <base>:<path>`), never from the checkout. That covers `.gitpro-policy.toml`, a `--policy` path inside the repo, and a relative `allowed_signers` such a policy names. A range that changes them is judged by the base version with a `⚠`. A policy the range adds is not enforced until merged (`⚠`, exit 0 unless another policy applies). A range with no single base is an error when the policy is in the repo. The base must be a commit of a protected branch: the Action's default `base.sha..head.sha` is one, and a custom range whose base the PR author chooses is not. CODEOWNERS on the policy file and `allowed_signers` is the documented protection. | A pull request must not be able to loosen the policy that judges it (add `gmail.com`, list its own key). The base is the reviewed, merged version, so the remaining trust is in who may merge policy changes. |
| 14 (round 2) | The CI signer check works by key fingerprint. Principals come from every base `allowed_signers` line whose key fingerprint equals `%GK`. OpenSSH pattern-list rules apply to their union: any matching `!pattern` denies, otherwise any match allows, case-insensitively. Lines whose `namespaces` exclude `git`, and `cert-authority` lines, are skipped. When no line matches (a certified key), `%GS` alone is compared. `valid-after`/`valid-before` are left to ssh-keygen. A committer email the key's principals do not allow is a violation (`allowed_signers`). | git does not bind an ssh signature to the committer email, and `%GS` holds only the first principal that verified, without the rest of a list or its `!` exclusions. |
| 14 (round 2) | The GitLab snippet's range base is `${CI_MERGE_REQUEST_TARGET_BRANCH_SHA:-$CI_MERGE_REQUEST_DIFF_BASE_SHA}`. The README's job runs gitpro as a non-root user (`useradd`, `su`) under `set -o pipefail`. | TARGET_BRANCH_SHA (merged results pipelines) is the target tip, so the current policy judges. DIFF_BASE_SHA, always set, is the fork point, so a policy tightened since then is not applied. Both are protected-branch commits. gitpro refuses root, and a pipe into `tee` would otherwise hide the exit code. |
| 14 (round 2) | `team --online` shows a result the forge did not give as `⚠` with `could not check (<reason>)`, never as not verified. The `verified` column is `·` when no rule has `require_verified_email`. The hint at the end names `gitpro check --policy FILE` for each failing policy file. | An unanswered question is not a failed check. The hint must be a command that runs as printed. |
| 15 | `registerLost` takes `(context, cli, caps)`. | `caps` decides whether the startup search runs. |
| 16 | `prompt` has a fourth state, `⚠ <id>`, for problems other than a wrong email. No identity stays `⚠ no identity`. The prompt cache is keyed by git dir (per worktree), not common dir. | Two worktrees of one repo can have different identities (`config.worktree`), and a signing or key problem is not a wrong email. |
| follow-ups (VS Code exec) | In VS Code, cancel (abort) sends SIGTERM only, never SIGKILL, so `gitpro clone` can stop git and ssh and remove its partial directory. A timeout or an output overflow sends SIGTERM and escalates to SIGKILL after 3 s (`KILL_GRACE`). `deactivate` sends SIGTERM to every live child's process group, waits 2 s, then sends SIGKILL. On POSIX each child leads its own process group, and kills go to the group. | A hard kill on cancel would leave a half-cloned directory behind. A stuck child must not hang the extension. A group kill reaches git's ssh, which would otherwise be orphaned. |
| 17 | The plugin manifest carries no `hooks` or `mcpServers` keys. `hooks/hooks.json` and `.mcp.json` sit at the plugin root, where Claude Code finds them by default. | Checked against the plugin layout as documented at release time. The docs were not fetched (the build runs offline), so recheck if the plugin does not load the hook. |
| 17 | `gitpro uninstall` removes the global guard files along with everything `apply` wrote (README "Undo everything"). It leaves per-repo guard blocks, agent hooks, MCP registrations, devcontainer edits, pins, `scan --fix` and `audit --rewrite` alone; each has its own undo. | This is how `plan.teardown` was built (01/06). The docs follow the code, not the earlier wording that the guard is not part of `uninstall`. |

# Decisions for 0.4.0 (spec 22), 2026-10-16

"Owner" marks a decision the product owner made. "Claude" marks a choice made
while writing the spec, which the owner has not confirmed. The 0.5.0 rows marked
"proposed, not decided" are not decisions.

| Topic | Decision | Who | Why |
|---|---|---|---|
| One surface | The terminal, VS Code and MCP use one command surface. A job has one command (spec 22 R1, R2). | Owner | The same job had different names in each place. |
| `setup` learns identities | `setup` offers to look through the user's repos and proposes identities. It reads local repos, the SSH config, `includeIf` rules and VS Code and JetBrains recents. It never reads private keys, shell history or forge accounts. | Owner | Typing hosts, owners and emails by hand is the slow part of setup. |
| Commit identity from the reflog | The commit identity of a repo comes from the `commit*` lines in the last 1 MiB of `logs/HEAD`. | Owner | The reflog records who actually committed. |
| Grouping | Identities are grouped by host, then owner. The most-used email is kept and the others show as "also seen". An owner with no email joins the host's identity if the host has exactly one, otherwise it is "not assigned". | Claude | Keeps the proposal short without guessing between emails. |
| `lost` folded in | `lost` becomes `scan --lost`. `--lost` with `--fix` is refused. | Owner | Lost work is a check on the repos `scan` already walks. |
| `unpin` folded in | `unpin` becomes `pin --remove`. `--remove` with `--remote` is refused. JSON `command` stays `unpin` in 0.4.x. | Owner (merge), Claude (the refusal and the JSON detail) | One command for the pin and its undo. |
| `audit --rewrite` | `audit --rewrite` becomes `audit --fix`. | Owner | Every check uses `--fix` for its fix (R5). |
| Consent in 0.4.x | `setup` follows R4. `pin`, `scan --fix` and `audit --fix` keep their 0.3 behavior in 0.4.x (a preview without `-y`) and also accept `-n`. | Claude | Changing the consent of existing writers is a separate decision. |
| Operation protocol | The agent operation protocol (preflight, run, change workflows) is deprecated. | Owner | Nothing used it. |
| Deprecate, then remove | Deprecated commands and MCP tools work in 0.4.0 with a warning, and are removed in 0.5.0. `GITPRO_NO_DEPRECATION=1` turns the warning off. | Owner | Gives users one release to move. |
| Team `check` stays | Only `check` without `--policy`, `--repo` or `--range` (the file drift check) is deprecated, for `setup -n`. The team policy check stays and is listed under "more". | Claude (open) | It is a feature CI runs, not a duplicate, and nothing replaces it. The owner may fold it elsewhere in 0.5.0. |
| No terminal | `setup` without a terminal and without `-y`/`-n` exits 2 and names both (0.3 printed a preview and exited 0). | Owner (rule), Claude (applied to setup) | "Never silently do nothing with exit 0" (cli-design skill §4). |
| `why --json` without a config | Still exit 2 with the error; the object also has the repo's `settings` and `remotes`. | Claude | The VS Code status bar falls back to them, as it did with `which --json`. |
| Devcontainer pin | The VS Code extension writes `initializeCommand` itself, after a modal that shows the line; for JSONC, unparseable or read-only files it offers Copy only. No backup or undo script in the repo. | Claude | `devcontainer` is deprecated; the extension is its only caller. |
| 0.5.0 aliases and tombstones | Proposed, not decided: keep `unpin`, `lost`, `audit --rewrite`, `check` and `apply` as aliases for a time, or leave tombstones that name the new command. | none yet | Spec 22 §10.4 leaves it open. |
